## 1. 背景和问题

GIF 动图标准制定于 1987 年（GIF87a/GIF89a），距今已有近 40 年历史。受限于其时代技术架构，GIF 存在三大先天短板：
1. **画质严重受限（256 色限制）**：GIF 动图调色板全局或每帧仅能容纳 256 色，复杂渐变或真实摄影画面必然产生明显色阶与颗粒噪点；
2. **压缩比低下（LZW 算法）**：GIF 采用古老的无损 LZW 算法，在应对高帧率或高清分辨率时体积动辄达到 10MB~30MB，极难满足现代社交媒体快速加载与传输要求；
3. **转码管线冗长（双阶段调色板提取）**：在 FFmpeg 中为了生成尚可观瞻的 GIF，必须强制运行两阶段流程（先采样计算 `palettegen`，再根据调色板进行 `paletteuse` 抖动拟合），导致 CPU 占用率高、转码耗时翻倍。

与此相对，Google 主导的 **WebP 动图（Animated WebP）** 格式已成为现代网络事实上的动图标准：
- **真彩色支持**：支持完整的 24-bit RGB 颜色（甚至带 8-bit Alpha 透明通道）；
- **极致压缩比**：在保持同等甚至更高视觉画质下，WebP 动图的体积仅为 GIF 的 1/3 ~ 1/2（节省 40% ~ 70% 空间）；
- **极速单阶段编码**：直接利用现代帧间/帧内预测与变换编码，省去耗时的调色板计算环节，导出耗时平均减少 50% 以上；
- **平台生态普及**：Telegram、Discord、小红书、微博、贴吧、各主流现代浏览器（Chrome、Safari、Firefox、Edge）均已原生支持 WebP 动图。

## 2. 用户与核心场景

- **场景 1：社交平台超小体积分享**
  用户制作了一个 5 秒的高清影视片段表情包，如果导出为 GIF 往往超过微信/Discord 的非会员上传体积限制（如 >5MB/10MB）；切换为 WebP 导出后，体积降至 1.5MB 以内，轻松完成秒传和流畅加载。
- **场景 2：丰富色彩与画质敏感型创作**
  用户截取了夜景霓虹或色彩渐变丰富的二次元动漫场景，在 GIF 下出现严重色斑和抖动噪波；切换为 WebP 格式后，色彩过渡平滑丝滑，毫无偏色和杂色抖动。
- **场景 3：快速批量制作与极速导出**
  用户需要连续截取多个短片进行表情包批量输出，WebP 免去了双通道调色板遍历生成环节，转码渲染速度大幅飙升，创作者无需忍受漫长等待。

## 3. 技术调研与对比

### 3.1 编码器与参数方案
内置的 FFmpeg static sidecar（针对 Apple Silicon 与 x86_64）已编译配置 `--enable-libwebp`，并且拥有 `libwebp` 和 `libwebp_anim` 编码器。

| 格式 | FFmpeg 编码器/滤镜参数 | 调色板需求 | 编码速度 | 循环参数 | 适用场景 |
|------|------------------------|------------|----------|----------|----------|
| **GIF** | `-f gif` + `split...palettegen...paletteuse` | 必须 | 慢（2 阶段） | `-loop 0` | 极高兼容性、古老论坛、旧设备 |
| **WebP** | `-c:v libwebp -loop 0 -q:v <50~90>` | **无需** | **快（单阶段）** | `-loop 0` | 现代社交媒体、小体积、高清真彩色 |

### 3.2 画质与压缩参数映射
`libwebp` 在动图编码中支持 `-q:v` 参数（0~100 质量值，默认通常为 75）：
- **low**: 映射为 `-q:v 55`（极限压缩体积，适合超大尺寸或极长动图）
- **medium**: 映射为 `-q:v 75`（画质与体积的黄金平衡点，体积大约为 GIF 的 30%~45%）
- **high**: 映射为 `-q:v 90`（几乎无损视觉观感，真彩色还原度极高）

### 3.3 滤镜图差异
- **GIF 滤镜图**：
  `[0:v]...[base];[base][sticker]overlay...[composed];[composed]split[s0][s1];[s0]palettegen...[palette];[s1][palette]paletteuse...[vout]`
- **WebP 滤镜图**：
  `[0:v]...[base]` 或包含贴图时 `...[composed]`。直接命名终点为 `[vout]`，完全剔除调色板拆分与合成节点，逻辑极其简洁。

### 3.4 本地预览与系统兼容性
- **Webview 兼容性**：WebKit（macOS Tauri 底层）已全面支持动态 WebP 播放；
- **缩略图 Base64 加载**：`src-tauri/src/lib.rs` 的 `read_file_as_data_url` 已内置对 `.webp` 返回 `image/webp` 扩展支持，开箱即用；
- **系统剪贴板与访达定位**：`reveal_in_dir` 和 `copy_file_to_clipboard` 是针对本地文件系统路径的操作，不限文件格式，天然支持 `.webp`。

## 4. 结论与决策

1. **核心定位**：在现有 GIF 流程基础上，以最小侵入、双格式平级支持的方式引入 WebP 动图导出；
2. **默认设置**：默认为 GIF 格式保持向后兼容；用户点击格式切换按钮即可一键切换至 WebP；
3. **输出联动**：切换格式时，自动联动输出路径后缀（`.gif` <-> `.webp`）；文件保存对话框筛选器动态匹配对应后缀；
4. **管线分离**：在 Rust 端依据计划格式（或扩展名）智能决定是否引入调色板，WebP 走极速直接编码管线；
5. **历史抽屉与标识**：历史记录卡片增加格式 Badge（`GIF` 或 `WEBP`），帮助创作者一目了然区分。
