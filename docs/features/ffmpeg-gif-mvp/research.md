# 需求调研：FFmpeg GIF MVP

- 状态：proposed
- Feature slug：ffmpeg-gif-mvp
- 分支：feature/ffmpeg-gif-mvp
- 负责人：待定
- 日期：2026-08-14

## 1. 背景和问题

Meme Studio 的核心方向是让用户把本地视频快速制作成可分享的 GIF。第一版需要先打通稳定、可验证的本地媒体处理链路，再逐步增加更丰富的时间线、图层和批处理能力。

## 2. 用户和场景

- 用户选择本地视频，截取一段时间范围并导出 GIF。
- 用户调整裁切区域、输出宽度和帧率，以控制画面和文件大小。
- 用户添加文字或 PNG 图案后导出可预览、可分享的 GIF。
- 用户希望看到处理进度，长任务可以取消，失败时知道原因。

## 3. 现有方案调研

FFmpeg 已覆盖视频探测、裁切、缩放、帧率转换、文字绘制、图像叠加和 GIF 调色板生成/应用等基础能力。GIF 的颜色数量和文件体积存在天然取舍，因此第一版应优先保证结果稳定和参数可解释，再增加更复杂的画质策略。

Tauri 适合将 Vue 编辑界面与本地 Rust 能力连接起来。FFmpeg 作为受控的本地 sidecar 进程，可以减少前端直接处理文件和进程生命周期的复杂度。

## 4. 技术调研

需要在编码前确认：

- FFmpeg 版本、构建目标和 macOS/Windows/Linux sidecar 命名；
- FFmpeg 构建的 LGPL/GPL/non-free 组合及随应用分发的许可证义务；
- 进度解析方式，以及未知时长、可变帧率和没有音频等输入的表现；
- 字体来源、字体文件选择和不同平台的字体差异；
- sidecar 的签名、打包、更新和失败诊断；
- 临时文件目录、取消时的子进程终止和残留清理。

## 5. 已确认事实

- 功能目标是本地视频到 GIF，不依赖云端上传。
- 基座使用 Tauri 2 + Vue + TypeScript。
- 媒体处理应由 FFmpeg 完成，Rust/Tauri 管理进程和文件。
- 需要裁切、压缩/尺寸调整、抽帧/帧率调整、文字和图案叠加。
- GIF 输出应优先使用调色板流程提升颜色质量。

## 6. 当前假设

- 第一版采用 FFmpeg CLI sidecar，而不是直接绑定 FFmpeg C API。
- 首批支持 macOS、Windows、Linux，但打包和签名验证需要分平台完成。
- 用户媒体默认只在本地处理，不进入项目仓库或远程服务。
- 第一版以单视频、单输出任务为主，不做批处理。

## 7. 未决问题

- 随应用分发的 FFmpeg 具体版本、构建来源和许可证审核结果是什么？
- 是否需要同时提供透明 GIF，以及透明度如何在 UI 中表达？
- 默认输出宽度、帧率和质量策略如何设定？
- 用户能否选择自定义字体文件？哪些字体随应用分发？
- sidecar 缺失、被系统拦截或版本不兼容时，如何提供可操作的诊断？

## 8. 调研结论和决策

| 结论/决策 | 理由 | 影响 |
| --- | --- | --- |
| 先实现单视频到 GIF 的 MVP | 先验证完整媒体闭环 | 暂不覆盖批处理和复杂时间线 |
| 使用结构化 FFmpeg 参数 | 降低路径、文本和命令注入风险 | Rust 需要维护参数构建和校验 |
| 默认采用 palettegen/paletteuse 流程 | 改善 GIF 颜色表现 | 任务需要临时调色板和更多进度阶段 |
| 将 sidecar、许可证和平台产物作为独立任务 | 这些事项会直接影响可分发性 | 未完成审核前不能宣称可发布 |
