# 开发流程规范

## 1. 目标和适用范围

本规范适用于 Meme Studio 的所有功能、重构、构建配置和文档变更。目标是让每次开发都具备：

- 清晰的目标和边界；
- 可追溯的需求、设计和实现决策；
- 独立、可回滚的 Git 分支；
- 可重复的自测证据；
- 明确的合并门槛和后续记录。

根目录 [AGENTS.md](../AGENTS.md) 是执行约束；根目录 [TODO.md](../TODO.md) 是产品方向和大任务清单；本文件是具体流程；每个功能目录下的五份文档是该功能的事实来源。

## 2. 功能状态

功能文档使用以下状态：

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| proposed | 已确认值得探索 | 完成需求调研 |
| researching | 正在确认用户问题、技术约束和风险 | 需求边界与验收标准可描述 |
| designed | 需求已确认，正在或已经完成方案设计 | 实现步骤和测试方案明确 |
| implementing | 已按设计编码 | 功能代码完成并进入验证 |
| verifying | 功能代码完成，正在运行自测 | 验收项全部通过或阻塞项有明确记录 |
| ready-to-merge | 自测完成，文档和变更范围已收敛 | 已合并到 main |
| merged | 已合并并同步记录 | 后续维护或新迭代重新建立变更 |

## 3. 阶段一：设定大方向 TODO

在开始具体功能前，先更新根目录 TODO.md。每个方向至少说明：

- 要解决的用户问题；
- 优先级和当前阶段；
- 主要交付物；
- 明确不做的事情；
- 下一步应该进入哪个 feature。

TODO.md 只保留产品方向和可观察的里程碑，不承载几十项实现细节。细化任务放在对应 feature 的 todo.md 中。

方向发生变化时，先更新 TODO.md，再调整功能文档和实现计划。已完成项目不要删除，保留完成标记和文档链接，便于回顾项目演进。

## 4. 阶段二：建立 feature 文档

每个功能必须创建：

~~~text
docs/features/<feature-slug>/
├── research.md
├── requirements.md
├── design.md
├── implementation.md
└── todo.md
~~~

feature-slug 使用小写 kebab-case，必须能从目录名看出功能主题。五份文档的职责如下。

### 4.1 research.md：需求调研

记录问题背景、目标用户和使用场景，梳理现有方案与技术资料，识别平台、依赖、许可证、性能和安全约束。把内容明确分为：

- 已确认事实；
- 当前假设；
- 尚未确认的问题；
- 已作出的决策及理由。

不确定的内容不能写成既定事实；外部资料、实验结果和样例文件要记录来源。

### 4.2 requirements.md：需求文档

记录功能目标、范围、用户故事、功能需求、非功能需求、错误和边界情况，以及可执行的验收标准。每个验收标准都应该能通过手工操作或自动化检查判断通过/失败。

需求范围变化时，先改需求文档，再改设计和 todo。超出当前功能范围的想法记录为后续事项，不直接混入实现。

### 4.3 design.md：设计文档

记录用户流程、模块边界、数据结构、Tauri command 和事件契约、进程管理、临时文件、权限、安全性、跨平台差异和关键取舍。

涉及媒体处理时，设计文档必须说明输入、输出、参数校验、进度、取消、失败清理和结果验证。涉及外部进程时，必须说明参数如何结构化传递，禁止把用户输入拼接成未经校验的 shell 命令。

### 4.4 implementation.md：详细实现文档

记录文件和模块计划、实现顺序、迁移/兼容方案、测试方案、实际自测结果、已知限制、风险和回滚方式。开发过程中以此文件记录事实，不用口头状态替代验证记录。

如果最终实现与设计不同，必须在这里写明差异、原因、影响和是否需要同步 design.md。

### 4.5 todo.md：细化 TODO

把实现拆成可独立勾选的原子任务。每项任务使用“动作 + 对象 + 完成条件”，例如：

- 为渲染任务增加取消入口，完成条件是取消后子进程退出且临时文件被清理；
- 为 GIF 输出增加可打开性检查，完成条件是无效输出被标记失败而不是显示成功。

todo.md 是开发期间的工作清单，不替代 requirements.md 的验收标准。

## 5. 阶段三：创建分支

开发前必须确认工作区没有与当前任务无关的未提交修改，并从最新 main 创建分支：

~~~bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/<feature-slug>
~~~

分支命名约定：

| 前缀 | 用途 |
| --- | --- |
| feature/ | 新功能 |
| fix/ | 缺陷修复 |
| refactor/ | 不改变产品行为的重构 |
| chore/ | 工程、依赖、构建或流程维护 |
| docs/ | 纯文档变更 |

一个分支尽量只服务一个 feature。若实现中发现另一个独立问题，记录下来并建立新的任务或分支，不把无关修改顺手带入。

## 6. 阶段四：实现功能

实现期间遵循以下规则：

1. 先按 feature 的 todo.md 推进；任务顺序或范围改变时立即更新 todo.md。
2. 用户可见行为、数据结构或模块边界改变时，先更新 requirements.md 或 design.md，再写代码。
3. 前端负责交互、状态展示和可序列化的编辑模型；Rust/Tauri 负责文件系统、外部进程和系统能力。
4. FFmpeg 参数使用结构化参数数组传递，不拼接未经校验的 shell 字符串。
5. 长任务必须有进行中、成功、失败和取消状态；需要时展示可解释的进度和错误摘要。
6. 临时文件、子进程和失败输出要能清理；取消和异常路径不能留下不可控的后台进程。
7. 用户媒体、密钥、令牌、构建产物、依赖目录和本地规划文件不能进入提交。
8. 新增依赖、二进制、字体或素材时，记录版本、来源、许可证和分发影响。
9. 实现完成后补齐 implementation.md 的真实文件清单和风险，不以“代码能编译”代替功能验证。

## 7. 阶段五：开发完成和自测

提交前至少执行：

~~~bash
git diff --check
pnpm install
pnpm build
PATH=/Users/ryantorres/.cargo/bin:$PATH cargo check --manifest-path src-tauri/Cargo.toml --locked
~~~

涉及桌面交互、文件选择、Tauri command 或外部进程时，还要运行：

~~~bash
pnpm tauri:dev
~~~

媒体处理功能至少覆盖以下验证：

- 正常短视频能导入并显示媒体信息；
- 裁切、尺寸、帧率、文字和图案参数确实影响输出；
- 输出文件存在、可打开、能播放/循环，且尺寸、帧率、时长符合设置；
- 正常完成时进度到达成功，失败时有可理解的错误；
- 取消后任务停止、临时文件清理、界面可再次开始任务；
- 缺少 FFmpeg、输入损坏、不支持格式和输出路径不可写时不会误报成功；
- 同一输入和参数重复执行时结果可解释且不会覆盖用户未确认的文件。

将命令、环境、结果、未覆盖的平台和阻塞项记录在 implementation.md。只有验收项通过，或剩余阻塞项已明确记录并获得接受，状态才可改为 ready-to-merge。

## 8. 阶段六：提交和合并 main

准备合并前检查：

- feature 五份文档已存在并与实现同步；
- requirements.md 的验收项都有结果；
- todo.md 已勾选完成或标出明确的后续项；
- TypeScript/Vite、Rust 和必要的桌面冒烟测试通过；
- git diff --check 通过；
- 未提交敏感文件、用户媒体、生成物或无关修改；
- 提交信息能说明变更目的。

推荐将分支推送到远程并通过 Pull Request 合并。没有 PR 流程时，使用本地合并：

~~~bash
git switch main
git pull --ff-only origin main
git merge --no-ff feature/<feature-slug> -m "merge: <feature-slug>"
git push origin main
~~~

合并成功后：

1. 将 feature 五份文档的状态更新为 merged；
2. 在根目录 TODO.md 更新里程碑和链接；
3. 确认 main 工作区干净并与远程同步；
4. 如不再需要，可删除已经合并的本地分支。

以下情况禁止合并：

- 没有对应的 feature 文档；
- 需求、设计和实现明显不一致且没有记录；
- 自测失败或错误路径未验证；
- 引入未确认许可证的二进制、字体或素材；
- 将密钥、令牌、用户媒体或构建产物提交；
- 把无关功能混入当前分支；
- 通过强制覆盖远程历史来绕过检查。

## 9. 例外处理

如果环境无法完成某项验证，不得伪造通过。应在 implementation.md 记录：

- 未能执行的命令；
- 具体环境限制；
- 已完成的替代验证；
- 对用户和发布的影响；
- 后续补测任务和责任边界。

阻塞项必须在最终提交说明和合并记录中再次可见。
